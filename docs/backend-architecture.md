# 后端架构

后端为移动端同步与 Web 管理提供统一服务。公共接口和字段定义见 [OpenAPI 契约](../openapi/openapi.yaml)，环境配置见 [后端说明](../backend/README.md)，部署和数据迁移见 [部署文档](../deploy/README.md)。

## 分层与依赖

| 层 | 职责 |
| --- | --- |
| `cmd/api`、`cmd/worker` | HTTP 服务与后台维护入口 |
| `internal/app`、`internal/config` | 依赖装配与配置读取 |
| `internal/handler` | 路由、请求解析、鉴权和响应 |
| `internal/service` | 密码身份、同步修订、冲突处理、余额与业务投影 |
| `internal/domain` | 状态模型、仓储与事务接口 |
| `internal/repository` | PostgreSQL 持久化、sqlc 查询、内存仓储 |
| `internal/schema` | 从 OpenAPI 派生同步字段和兼容规则 |
| `migrations` | 带版本与校验和的数据库迁移 |

PostgreSQL 使用 pgx v5 的 `database/sql` 适配器。账号、设备、身份、会话与统计等固定查询由 sqlc 生成；动态业务字段使用契约白名单构建 SQL，标识符引用与值参数化分别处理，两类查询共用连接池和事务。

## 数据存储

21 个业务实体分别存储于结构化表：

| 业务 | 表 |
| --- | --- |
| 账单与储值 | `bills`、`stored_value_accounts`、`stored_value_adjustments` |
| 日记 | `diary_entries`、`diary_tags`、`diary_links` |
| 饮食 | `food_entries`、`food_day_records` |
| 提醒与纪念日 | `reminders`、`reminder_completions`、`anniversaries` |
| 决策 | `decision_collections`、`decision_options`、`decision_choice_records` |
| 物品 | `item_categories`、`stored_items` |
| 轨迹 | `tracks`、`track_points`、`track_segments` |
| 媒体元数据 | `media_assets`、`media_attachments` |

记录保留字符串 ID，金额使用整数分，业务时间使用毫秒整数。业务表中的 `tenant_id` 表示数据账号；储值调整中的 `account_id` 表示业务储值账户。

已知字段存储于业务列，`extras JSONB` 保存未知字段，`present_fields` 区分字段缺省与显式 null。`row_state` 是以调用者权限执行的快照视图，从业务列和扩展字段重建同步状态。

| 辅助存储 | 用途 |
| --- | --- |
| `account`、`devices` | 数据账号、恢复凭据和长期设备凭据 |
| `users`、`sessions` | 密码身份与可过期 Web 会话 |
| `change_log` | 按账号单调递增的修订历史和墓碑 |
| `change_events` | 与历史修订关联的时间、操作和来源元数据 |
| `mutation_receipts` | 请求摘要与幂等结果 |
| `sync_metadata` | 数据集世代与同步水位 |
| `media_objects` | 账号范围内的媒体对象索引 |

媒体字节按账号与 SHA-256 存放在文件系统，业务记录只保存媒体引用。数据库迁移与媒体迁移分别处理，两者没有共同事务。

## 账号隔离与身份

业务表、同步历史、回执、媒体索引及同步元数据开启强制 RLS。服务从设备 token 或 Web 会话解析数据账号，并在事务内设置账号上下文；请求体不能指定数据归属。业务依赖在同一账号范围内检查。

运行角色不能是超级用户、拥有 BYPASSRLS、拥有业务表或继承表所有者权限。DDL 由独立迁移角色执行，普通启动检查迁移版本与校验和。

设备初始化、恢复密钥、配对码与长期设备 token 提供设备登录。用户名密码绑定到原数据账号，或通过注册创建新数据账号；用户名不能自动关联旧数据。

密码使用随机盐和 Argon2id。Web 会话独立于长期设备凭据，默认使用 HttpOnly、Secure、SameSite=Strict Cookie，也支持 Bearer 凭据。Cookie 写请求检查 Origin，登录和注册请求携带 Origin 时也检查来源。退出和改密吊销 Web 会话；设备凭据由设备管理单独吊销。

Web 会话保存服务端授权的 `access`。新登录及旧会话升级后采用 `read_only`：允许业务查询、统计、历史、媒体读取、退出及更新当前设备来源资料，禁止业务写入、同步上传、媒体修改、账号导出、改密与设备管理。只读限制由鉴权中间件执行，Cookie 和 Bearer 一致；长期设备凭据保持原权限，Header 不参与授权。

## 资源 CRUD 与同步修订

资源路径将表名中的下划线转换为连字符。例如 `bills` 对应 `/api/bills`，`stored_value_accounts` 对应 `/api/stored-value-accounts`。

| 操作 | 请求 | 行为 |
| --- | --- | --- |
| 列表 | `GET /api/bills` | 当前账号下的分页、搜索、日期筛选 |
| 详情 | `GET /api/bills/{id}` | 返回快照与服务器版本 |
| 新增 | `POST /api/bills` | 携带完整快照与 `base_version=0` |
| 修改 | `PUT /api/bills/{id}` | 基于详情快照和最近确认的版本提交 |
| 删除 | `DELETE /api/bills/{id}` | 基于最近确认的版本写墓碑，保留历史 |

写入信封包含 `mutation_id`、`base_version`、`data_version`、`updated_at_ms` 和 `snapshot`。删除无需快照。服务端为资源写入设置权威设备 ID 和更新时间。

所有写入复用同步修订事务：检查契约和依赖，读取幂等回执，核对 `base_version`，合并未知字段，执行余额与业务投影，更新业务行、版本、历史和回执。任一步失败时回滚事务。

相同 `mutation_id` 和内容重试返回原回执。相同 ID 被用于不同请求时拒绝写入。版本过期时按三方规则处理；有争议时资源接口返回 HTTP 409，同步批量接口按条返回 conflict；内容已一致返回 duplicate；缺少业务依赖返回 HTTP 422。资源写入产生的修订可由设备通过增量接口读取。

### 并发修改与人工确认

共同基础来自 `change_log` 中与当前账号、表、记录 ID 和 `base_version` 精确匹配的历史快照。基础不存在或已经是墓碑时保持保守处理。设备时间和设备标识只记录来源，不决定哪一端覆盖另一端。

独立字段修改自动合并，双方把同一字段改成相同值时接受该值。双方对同一字段改成不同值时返回冲突，不提前写入部分修改。同步元数据、余额和打卡派生集合不参与业务差异判断；未提交字段保留基础值，显式 null 表示清空，未知字段和整数精度继续保留。

账单原价、优惠、实付、收支类型、分类、支付方式、储值账户、结算状态、有效期、核销时间和退款原因作为一个结算组比较。修改标题或备注可以与金额修改合并；双方修改结算组且最终值不一致时必须选择整组。储值影响由服务端基于当前账单和最终账单重新计算，继承历史累计影响，不采信过期设备提交的累计扣款。

人工确认创建新的 mutation_id，仍携带原基础版本，并提供 `resolution=local|remote` 和 `expected_version`。expected_version 必须等于用户展示的云端版本，核对、合并、财务投影和写回在同一账号锁与事务中完成；云端已变化时重新返回冲突。选择只作用于争议字段或结算组，独立修改始终保留。删除冲突和缺少共同基础的冲突选择整条记录。

客户端冻结已经准备的请求以保证重试幂等。收到权威回执后，把后续尚未上传的独立编辑衔接到合并快照，并同步本地可见记录。上传期间出现的新争议继续携带原基础版本，由后端返回冲突；不会仅提升版本号而丢弃比较依据。原始本地编辑保留在变更日志中，确认页面也检查本地内容与展示时是否一致。

能力接口通过 `three_way_merge` 和 `conflict_resolution` 标识上述行为。人工确认前客户端核对服务端能力，避免旧服务端忽略新增确认参数。

账单接口接收契约定义的完整快照，包括收支类型、金额、发生时间和结算状态。储值影响沿用同步修订规则，`stored_value_effects` 使用 JSON 编码字符串记录各储值账户的整数影响。接口没有单独的简化账单表单协议。

列表按 ID 升序分页，使用 `limit`、`cursor`、`q`、`from_ms`、`to_ms`。日期筛选优先使用业务发生时间。基础统计的记录数量按更新时间统计；账单金额按 `occurred_at` 的左闭右开区间汇总，排除退款和墓碑。

## 云端变更历史

`change_log` 继续承担同步与三方合并，`change_events` 通过账号和版本关联其不可变快照，不重复保存完整业务内容。事件、业务修订与 `mutation_receipts` 在同一事务提交。只有实际写入的修订创建事件，相同 mutation 重试返回原事件 ID 和服务端时间；冲突、校验失败、依赖缺失及无变化的 duplicate 不新增事件。

事件使用独立 ID，并保存数据集世代、前一云端版本、客户端修改时间、服务端接受时间、标题摘要和操作类型。新增、修改、删除、墓碑恢复与处理方式分开记录；自动合并、人工确认和系统派生具有明确标识。系统派生事件共享触发 mutation 和操作 ID，指向主事件，不沿用派生行的旧设备与旧修改时间作为用户来源。

来源分为随 mutation 冻结的 `origin` 和此次鉴权提交身份。原始来源标识不直接连接服务端 `devices.id`；提交设备和会话从服务端鉴权上下文获取。请求 Header 仅描述提交环境，资源 CRUD 的在线编辑可使用该请求的来源；同步上传不能用 Header 推断原始离线来源。设备名称、系统和版本按事件保存，解绑、改名或会话删除不会改变已有历史。来源字段不参与权限判断，Header 不进入 mutation 请求摘要；可选 `origin` 进入新 mutation 摘要，缺省时保持旧请求兼容。

`GET /api/change-events` 按修订版本倒序返回摘要，可按实体、记录、操作、原始平台、提交设备和服务端时间筛选。分页固定首次请求的云端版本，游标绑定账号、世代和筛选条件；清空后旧游标返回 `reset_required`。`GET /api/change-events/{event_id}` 按事件关联读取提交前和最终提交快照，返回字段差异与关联事件，避免用后来变化的当前行解释旧操作。字段差异隐藏同步技术元数据，保留缺省与 null 的区别、未知字段和精确数字。

能力通过 `change_history_v1` 和 `mutation_origin_v1` 声明。新客户端发送原始来源前检查能力；旧客户端继续同步，未上报的平台保存为 unknown。升级为旧快照补充独立事件关联和可确定的版本顺序，不推算缺失的服务端接受时间或鉴权来源，旧处理方式标为 unknown。

事件表开启强制 RLS，并使用账号、实体、提交时间、来源及操作关联索引。账号 SQL 导出包含事件元数据、历史快照的契约版本及回执关联；全实例备份继续通过数据库备份包含事件表。恢复需保留事件与世代关联；清空云端在同一事务删除本账号事件、历史、回执及业务数据。已发布初始迁移保持不变，事件表与会话范围通过新增迁移提供。

设备可以登记 `profile` 中的客户端、系统、版本和安装来源标识。初始化、配对、恢复及登录读取来源 Header，`PUT /api/devices/current/profile` 只更新当前鉴权设备的资料。浏览器会话的客户端类型始终为 web，不能通过来源 Header 或资料登记绕过权限。`device_profiles_v1` 供新客户端协商支持情况。历史在提交时按当前账号内的来源标识与平台进行唯一匹配，并冻结可选的 `original_registered_device_id`；多重匹配或未登记来源保留未知，关联只用于展示。

移动端在本地编辑事务内保存来源资料，并在 outbox 入队时复制；冻结上传请求后不会因 App 更新、系统更新或能力升级而改变请求内容。可移植备份通过 `record_origins` 保留与实体、设备标识和修改时间一致的来源，选择性恢复保留本机已有记录来源。旧备份和缺少元数据的变更不使用导出设备或上传设备补齐原始来源。

运行日志使用服务端生成的请求 ID，响应通过 `X-Request-Id` 返回该关联值。日志包含 HTTP 状态、响应字节、耗时、鉴权账号和设备，以及批量同步中各 mutation 状态的计数；不包含查询参数、密码、token、Cookie、完整请求或业务响应。

## 备份恢复后的差异同步

首次绑定或恢复备份后，客户端先获取云端的数据目录，已有相同内容无需完整传输。目录对应同步开始时的同一云端版本 W；分页期间新增的变化，在目录处理完成后从 W 继续增量拉取。这就是协议中“固定水位”的含义。

`manifest_bootstrap_v1` 能力提供两个接口：

- `GET /api/sync/manifests?generation=…&watermark=W&after=…&limit=500`：返回截至 W 各记录的最新版本、删除状态、内容摘要及必要的传输元数据，包含墓碑。
- `POST /api/sync/snapshot-queries`：携带 generation、watermark 和 1–500 个不重复的版本，按请求顺序返回本账号内相应的不可变历史快照，不读取该记录后来变化的当前状态。

客户端仅对相同数据契约、摘要相同且尚未发送的本地盘点项建立同步基线，标为 `matched`。这表示云端已有相同内容，不伪造服务端 mutation 回执，也不产生新修订。匹配状态、关联 inbox 与页面进度在同一事务落地；对账期间产生的新编辑保留，并衔接到已确认相同的云端版本。已经冻结的上传请求不能被盘点跳过。

不同内容、缺失记录和墓碑按需获取完整快照，复用现有 inbox、依赖校验和冲突处理。不能把旧备份整行内容标为基于最新云端的编辑。原始目录和待接收页面保留用于重试，完成后清理；清空云端或世代变化沿用原有重建规则。旧服务端无此能力时继续使用原快照流程。

### 内容摘要协议 v1

摘要包含完整业务快照、派生结果和未知字段，仅移除顶层 `updated_at`、`device_id`、`server_version`、`sync_status`。这些字段以目录的 `metadata` 对象单独返回，保留缺省与 null 的区别，用于恢复准确的云端 shadow。其他字段、嵌套内容和删除状态不能忽略。

对移除四个字段后的 JSON 对象进行如下编码，然后计算编码 UTF-8 字节的 SHA-256，输出 64 位小写十六进制：

| JSON 值 | 编码 |
| --- | --- |
| null | `z` |
| true / false | `t` / `f` |
| 字符串 | `s<UTF-8 字节数>:<原字符串>`，不转义、不做 Unicode 归一化 |
| 数字 | `n<系数>e<十进制指数>;`；去除无意义的前后零，0 和负零均为 `n0e0;` |
| 数组 | `a<元素数>[<依次编码的元素>]` |
| 对象 | `o<键数>{<依次编码的键和值>}`；键按 UTF-8 字节顺序排列 |

例如 `1`、`1.0`、`1e0` 均编码为 `n1e0;`，`1000` 编码为 `n1e3;`。金额大整数不经 Double 转换。三端使用共享摘要测试向量，明确验证 null、数组、Unicode、科学计数法和大整数。无法精确比较时获取完整快照，不能猜测为相同。Swift 字典无法保留同一对象内规范等价的两种 Unicode 键，这类快照不会匹配服务端摘要，会回退到原完整快照路径。

媒体按原有内容地址处理：本地先校验 checksum 和大小；上传前 HEAD 核对服务端声明的 ETag 与长度，服务端检查实际文件是否存在且长度一致，避免重复上传已存在对象。HEAD 不逐次重新计算云端文件的完整摘要。下载时复用本地已校验对象。媒体与数据库的事务边界继续沿用现有规则。

## 契约与演进

`openapi/openapi.yaml` 是公共字段与接口的唯一来源，`x-recoow-sync` 定义实体版本、依赖和兼容规则。各端类型和同步注册表由契约生成，数据库迁移分别维护。

未知字段在读写和同步过程中保留。新增字段应更新契约和相应数据库迁移；破坏性变更需要显式版本转换。客户端通过同步能力接口核对实体版本、世代与协议能力，接口路径变更须与客户端适配一起部署。

全实例备份使用 PostgreSQL custom dump 和媒体目录，包含身份与凭据；账号 SQL 导出用于恢复本账号业务数据。恢复旧备份后更换数据集世代，避免客户端复用已见过的版本水位。源库和原媒体在迁移时保留，具体操作见部署文档。
